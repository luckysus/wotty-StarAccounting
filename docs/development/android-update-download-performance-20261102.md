# Android 应用内更新下载性能修复

## 问题与目标

- 官网 APK 直链约 7.1 MB，本机实测约 2 秒完成，服务端响应和缓存正常。
- App 内更新使用自建 `HttpURLConnection` 下载链路，与浏览器调用的 Android 系统下载器不同，弱网恢复、后台下载和连接调度能力较弱。
- Android 安装包已经是 `versionCode 168`，前端版本常量仍为 `167`，导致最新版可能再次收到同一安装包的更新提示，下载完成后又无法通过“新版本必须高于已安装版本”的校验。
- 用户要求撤回并重新发布同名 `0.8.1-beta.2`，不增加 beta 序号。手机已安装内部检查包 `versionCode 169`，因此重发包使用 `versionCode 170`。

本次目标是让 App 内更新使用 Android 系统下载器，继续在弹窗内显示真实进度与实时速度，并以手机实际安装的版本号判断更新。

## 修改分类与版本

- 分类：修复 / PATCH。现有应用内更新下载速度和版本识别未按预期工作，用户完成的任务没有变化。
- 重发版本名：`0.8.1-beta.2`。
- Android `versionCode`：`170`，确保已有 `168` 和内部检查包 `169` 都能识别该包为升级。

## 实施步骤

1. 将原生更新插件的自建网络流替换为 Android `DownloadManager`，下载到应用专属外部目录，保留 HTTPS 校验、APK 包名和版本校验以及系统安装界面。
2. 查询系统下载任务状态并向 Web 层发送下载字节数、总字节数、百分比和实时速度；下载停滞或系统报告失败时返回明确错误。
3. 通过 Android 插件读取实际安装包版本；前端判断和显示均使用该值，并同步前端常量、包版本和 `versionCode`。
4. 在更新弹窗中显示实际下载速度，保留浏览器下载后路。
5. 更新简短版本记录，执行 Android 发布检查与构建；如手机可连接，再进行真机安装验证。
6. 保留历史安装包，清理临时文件并先在本地仓库提交。
7. 撤回 GitHub 上现有 `0.8.1-beta.2`，以同名标签从已提交源码重新构建签名包并发布；同步更新版本服务的 APK 地址和 `versionCode`，核对可下载性。

## 验收标准

- 已安装版本与服务端版本相同时不再提示更新。
- App 内下载由 Android 系统下载器负责，速度应接近手机浏览器下载同一 URL 的表现。
- 弹窗持续显示百分比和实时速度，下载完成后打开系统安装界面。
- 下载失败、停滞和 APK 校验失败均可重试，且浏览器下载入口继续可用。
